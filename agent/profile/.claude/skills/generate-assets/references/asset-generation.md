# 生成资产图

为项目的角色、场景、道具、商品创建资产图，保证整个视频中视觉元素的一致性。
图像供应商由项目设置选择（不锁定具体 backend）。

> Prompt 编写原则详见 `.claude/references/generation-modes.md` 的"Prompt 语言"章节。

## 共同约定

- 所有资产 `description` 用**叙事式段落**，而不是关键词列表。
- `description` 只写可见细节，角色写明性别；多面道具写清每面的结构与零件位置。角色声音单独写在 `voice_style`。服务端统一拼装画风、版式、背景和布光。
- MiniMax-H3-Image 使用自然语言。有参考图时按实际附件顺序用「图1」等称呼，写清保留什么、改变什么；没有参考图时只描述目标画面。
- Pending 判定：Artifact Manifest 中该资产图状态为 `missing`（含登记了文件却读不到）；`stale` 产物复用，不计入待生成。
- 衍生（`本体/衍生`）与本体同批：本体也待生成时，本体图成功后衍生才提交；本体失败则衍生报 `generation_dependency_failed`，不提交。

## 角色（character）

### description 编写指南

将 `description` 写成三段，分别描述性别与年龄及体态、面部特写、发型与服装。面部段写清正面平视，从发顶取到上胸，脸占主要画幅，头部、颈部、双肩与衣领自然相连。依次描述脸型与下颌、额头与发际线、眉形、眼形与瞳色、鼻梁鼻尖、唇形、肤色和表情，结合原图突出可辨识特征。全身段写明发型、分层服装、颜色、面料、配饰和自然站姿。

单独写入 `voice_style`。为会说话的角色设定听感年龄、音高、音色、语速、停顿、吐字、气息、句尾及常态情绪，即使本集没有台词也填写。根据已有声音设定和性格设计可供 TTS 执行的描述。

### 生成角色参考音频

用户要求生成或重生成角色参考音频时，先核对角色的 `voice_style`，缺少时依据已确认的角色设定补齐。调用 `mcp__juling__generate_character_reference_audio`，传角色 `name` 和一两句符合角色的简短朗读 `text`。默认按音频模型能力设计或匹配音色。任务成功后自动写入 `reference_audio`，用户可在角色详情试听；有生成批次回执时查询终态后再报告结果。

### 输出布局

保持项目当前画布宽高比。较宽画布横排四格，首格为连同颈肩和衣领的放大正脸特写，约占总宽的 36%。右侧三格等宽，依次为正面、90° 正侧面、背面全身。较窄画布按相同顺序使用 2×2。四格的脸型和发型一致，全身三格的头身比、服装与配饰一致。

## 场景（scene）

### description 编写指南

写明时代、空间结构、建筑与陈设，从前景到远景交代位置关系，再写时段、天气、光源与色调。环境为主，不写入戏人物和动作。

**示例**：

> "村口的百年老槐树，树干粗壮需三人合抱，树皮龟裂沧桑。主干上有一道明显的雷击焦痕，从顶部蜿蜒而下。树冠茂密，夏日里洒下斑驳的树影。"

### 输出布局

单张广角环境全景空镜，空间纵深清楚。

---

## 道具（prop）

### description 编写指南

写明尺度、长宽厚比例、配色、材质、纹理、零件连接与当前开合状态。以正面为左右基准，分六面写零件的数量、位置、相对尺寸、方向和跨面连接。把立体道具的四格构图写进 `description`，逐格写可见面及该物体实际可见的部件。

**示例**：

> "一块翠绿色的祖传玉佩，约拇指大小，玉质温润透亮。表面雕刻着精致的莲花纹样，花瓣层层舒展。玉佩上系着一根红色丝绳，打着传统的中国结。"

### 输出布局

在项目现有画布内用 2×2 等大四格。左上为正面垂直平视，右上为背面垂直平视。左下从左前方约 45°、向下约 30° 看正面、左侧和顶面。右下从右后方约 45°、向上约 30° 看背面、右侧和底面。各格统一比例尺与长宽厚比例，保留同一开合状态。各面无明显差异的平面道具可用单视图。

---

## 商品（product）

### description 编写指南

按商品六面描述已确认的细节，写清长宽厚比例、材质、部件数量、位置、相对尺寸、朝向，以及标识、接缝与纹理的跨面关系。商品原图是细节与比例的基准。

### 输出布局

统一浅灰棚拍背景，2×2 四视图。左上正面、右上背面、左下左前上方、右下右后下方，合计展示六面。扁平或对称商品也使用四格。

## 工具调用

入队走 MCP 工具：

| 操作 | 工具 |
|------|------|
| 列出所有/某类 pending | `mcp__juling__list_pending_assets({"type": "character"})`（type 可省略） |
| 列出本集引用的 pending | `mcp__juling__list_pending_assets({"episode_id": 3})` |
| 生成本集引用的全部 pending（含商品与衍生） | `mcp__juling__generate_assets({"episode_id": 3})` |
| 生成所有 pending（四类各一轮） | `mcp__juling__generate_assets({})` |
| 生成某类全部 pending | `mcp__juling__generate_assets({"type": "character"})` |
| 生成指定多个 | `mcp__juling__generate_assets({"type": "prop", "names": ["玉佩", "密信"]})` |
| 生成单个 | `mcp__juling__generate_assets({"type": "scene", "names": ["村口老槐树"]})` |
| 生成单个商品 | `mcp__juling__generate_assets({"type": "product", "names": ["保温杯"]})` |
| 生成衍生 | `mcp__juling__generate_assets({"type": "character", "names": ["张三/战损"]})` |

`episode_id` 不与 `type` / `names` 同用；「本集引用了哪些资产」由服务端计算，与 Web 集层同一份名单。

结果按 `requested / succeeded / failed / blocked / skipped` 逐 ID 返回，ID 形如 `character/张三`（衍生为 `character/张三/战损`）；
已失效但可复用的旧图进入 `skipped`，不会自动重生；
按每一项自带的 `problem.code` 与 `problem.action` 决定下一步，不要解析文本。
结构详见 `.claude/references/generation-results.md`。

## 工作流程

1. **加载项目元数据** — 从 Artifact Manifest 找出资产图状态为 `missing` 的资产
2. **入队生成任务** — 只提交资产名；server 执行时按项目里存储的 description 渲染（`lib.prompts.prompt_builders` 注入布局 / 防崩 / 反向）。声明了原图却读不到时生成被拒（`asset_original_missing`），让用户重新上传原图或清掉原图字段
3. **审核检查点** — 按「审核检查点：审图」派审图子智能体看图，把报告与重新生成建议交给用户确认；用户可批准、要求重新生成，或要求编辑
4. **更新 project.json** — 更新 `character_sheet` / `scene_sheet` / `prop_sheet` / `product_sheet` 路径

## 审核检查点：审图

资产图生成完成后，先由只读的审图子智能体 `review-images` 看图，再把结论交给用户确认。审图不会触发生成或编辑，不产生生成费用；子智能体看图的模型调用照常计入 Agent 会话用量。

1. **派发**：由主 Agent 派发（子智能体不能再派子智能体：本 skill 在生成子智能体里执行时，生成结果交回主 Agent 后由主 Agent 派发）。只派本轮生成成功的资产，每组同一类型、至多 20 张；有多组时在同一条消息里为每组各发起一次 `review-images` 调用，让各组并行。派发消息写明图片类型（`character` / `scene` / `prop` / `product` / `character_derivative`）、本组资产名（衍生写「本体名/衍生名」）和用户的关注点。
2. **交给用户**：把各组报告汇总给用户：哪些可用，哪些建议重新生成或编辑、原因是什么，哪些存疑。有建议重新生成、编辑或存疑的资产时，用 AskUserQuestion 多选（`multiSelect: true`）请用户勾选要处理的资产，每个选项写明资产名、原因与建议的处理方式。用户确认前不重新生成，也不编辑。
3. **执行**：按用户勾选的资产与下一节「编辑 vs 重新生成」处理。处理完成后，可以对新版本再派一次 `review-images` 验收。

用户追问某几张资产图时，用 `mcp__juling__inspect_images` 直接看图回答，不必派发子智能体。

## 审核检查点：编辑 vs 重新生成

用户对资产图提意见时先判断诉求类型，选错路径会推翻已满意的部分或丢掉预期外的改动：

- **只想改局部**（换发色、去掉杂物、调整光线氛围等），且构图和整体设计满意 → 用
  `mcp__juling__edit_images({"resource_type": "character", "edits": [{"id": "张三", "instruction": "把头发改成红色"}]})`
  保底图微调，一次可对同类型多个资产批量下发
- **想推翻构图/整体设计重来**，或本来就要改 description（进而改变后续按 description
  重新生成的结果）→ 用 `generate_assets` 按更新后的 description 重新生成整图
- 编辑不会更新 `description` / prompt——编辑后再触发 `generate_assets` 仍按原 description
  重画，编辑效果只能从版本历史找回

## 质量检查

- **角色**的首格为带颈肩和衣领的自然正脸肖像，其余三格展示从发顶到鞋底的正面、90° 正侧面和背面全身。全身三格等比例，四格的身份和外观与设定一致。
- **场景**：整体构图和标志性特征突出、光线氛围合适
- **道具**的四格覆盖六面，核对平视和斜视的可见面区别、零件位置、长宽厚比例、材质和开合状态。
- **商品**：逐格对照原图核对细节与长宽厚比例，特别检查部件数量、相对尺寸、位置、朝向和跨面连续性。四格的商品状态、品牌、文字、配色、材质与结构一致。画面只呈现商品本体与指定背景。
